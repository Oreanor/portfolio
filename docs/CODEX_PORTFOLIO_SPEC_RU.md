# ТЗ для Codex — портфолио Sergei Nikonets

**Версия:** 2.0 / Codex · 16 ноября 2026 года  
**Цель:** создать полноценный, быстрый, выразительный веб-сайт-портфолио старшего frontend-разработчика и автора независимых цифровых продуктов.  
**Язык сайта:** английский. **Язык этого ТЗ:** русский.  
**Входные материалы:** этот документ, `portfolio_project_content.json`, `sergei_portfolio_preview.html`, а при наличии — оригинальные README проектов, CV и настоящие скриншоты.

## Codex: как использовать этот комплект

Это **задача на непосредственную реализацию**, а не приглашение написать ещё одно ТЗ. `CODEX_START_PROMPT.txt` — сообщение, которое пользователь отправляет агенту; `AGENTS.md` — репозиторные инструкции; данный документ — спецификация; `sergei_portfolio_preview.html` — только пример UX/стиля; `portfolio_project_content.json` — вспомогательные краткие данные.

**Если JSON не скачался, обрезался или недоступен:** НЕ останавливай работу. В разделе 3 ниже есть полный список всех десяти проектов, их различающие особенности и технические решения. Можно восстановить `src/content/projects.ts` прямо из данного документа. Отсутствие JSON **не блокер**. Не нужно копировать исходный JSON в клиентский bundle, если удобнее typed TS.

**Правила для Codex:**

- Не ограничивайся рассуждениями: пиши код, запускай проверки, исправляй найденные ошибки. Не проси согласования каждого шага.
- Сначала изучи репозиторий и локальные README; не затирай существующий код, assets, `.env` и историю Git. Не коммить, не пушь и не деплой без команды пользователя.
- В случае отсутствия фото/видео — честные нейтральные placeholders с подписью `Screenshot coming soon`. **Не использовать изображения из HTML-прототипа как доказательство внешнего вида реального приложения.**
- Не добавляй «Featured», «Other» или «Playground» для второстепенных работ: **все 10 равноправны**. Категории служат лишь фильтрам.
- Все десять индивидуальных страниц имеют **собственный подробный контент**, а не повторяющиеся маркетинговые блоки.
- Нужны настоящие действия у кнопок/ссылок. Если URL не проверен — не рисовать активную ссылку. Не изобретать метрики.
- Принимая технические решения, предпочитай небольшие понятные компоненты, типизированные данные и минимальный JS, а не дополнительные библиотеки без необходимости.

## 0. Главный принцип

**Показать ВСЕ десять проектов. Никакой выборки “featured”, никакого топ-5 и никакого раздела для второсортных работ.** Каждый проект — отдельный продукт со своим характером, интерактивными особенностями, инженерными решениями и собственной страницей. Категории используются только для навигации. Все 10 карточек одинакового визуального статуса, все видны на главной по умолчанию.

Портфолио должно показывать не просто владение React/Next.js, но диапазон задач: сложные интерфейсы, локализацию, работу с данными, браузерные API, AI-интеграции, математические симуляции, 2D/3D, игровые правила, UX/UI и самостоятельную продуктовую разработку.

Важно корректно раскрывать AI-assisted workflow: автор формулирует идеи, продуктовые требования, UX/UI, архитектурные приоритеты, ведёт итерации, проверяет качество, координирует разработку; AI-агенты помогают писать существенную часть кода. Не приписывать автору ручное написание всего кода, но и не изображать его как человека, который просто «ввёл промпт».

### Страницы проектов (`/projects/[slug]`)

У всех десяти единый каркас, но различающееся содержание:

- название, тип, одна сильная смысловая фраза;
- **реальные** изображения интерфейса / сцены игры / 10–25-секундный ролик; медиагалерея с подписями к тому, что изображено;
- **The idea:** зачем продукт существует и какое необычное пользовательское действие лежало в основе;
- **What makes it different:** 3–6 специфических возможностей, не список модных слов;
- **Engineering / design decisions:** 2–4 конкретных решения с причиной и компромиссом;
- **How I worked:** что было создано и спроектировано автором и как использовались AI-агенты;
- **Stack:** компактные технологические теги;
- **Status / links:** Live demo, repository, desktop download, video — показывать только существующие и проверенные ссылки; иначе не рисовать неработающие кнопки;
- ненавязчивая навигация к следующему проекту + назад ко всем.

## 4. Визуальный стиль

Референс — HTML-макет из вложения, но допускается доработка при сохранении его сильных решений.

- **Тон:** editorial / clean engineering / digital craftsmanship, не шаблонный «программистский лендинг».
- **Фон:** светлый, слегка тёплый (например `#f7f6f2`), основной текст тёмно-зелёно-графитовый (`#19211f`), зелёный акцент (`#216f62`), деликатные линии.
- **Типографика:** крупный чёткий sans-serif + дозированная курсивная serif в hero; никаких кислотных градиентов, чрезмерного glassmorphism, прыгающих букв и стартового 3D-лоадера.
- **Карточки:** единая визуальная важность и ширина; выразительная картинка 16:10 или схожая, название, одна фраза, 2–4 тега; при наведении мягкий сдвиг, не скачки интерфейса.
- **Группировка:** одна общая сетка + фильтры (10/3/2/5); в режиме All порядок может следовать драматургии разнообразия, но не создавать «первый сорт / второй сорт».
- **Медиа:** настоящие скриншоты приложений и кадров из игр; 2–4 на проект, при наличии короткие видеоклипы. Прототипные изображения в HTML — только условные арт-заглушки, не выдавать их за настоящие скриншоты.
- **Адаптив:** 2 колонки на desktop, одна на mobile, читабельные шрифты, доступные интерактивные элементы.
- **Анимации:** минимальные и полезные, respect `prefers-reduced-motion`; никаких непрерывных тяжёлых эффектов.

## 5. Техническая реализация

Предпочтительно Next.js App Router + TypeScript + Tailwind CSS, с поддерживаемыми на дату разработки версиями и строгим typecheck. CMS не нужна. Важнее чистая архитектура и качество, чем сложные зависимости.

Предлагаемая структура:

```text
src/
  app/
    page.tsx
    about/page.tsx
    projects/[slug]/page.tsx
    layout.tsx
    sitemap.ts
    robots.ts
  components/
    Header.tsx
    Footer.tsx
    Hero.tsx
    ProjectGrid.tsx
    ProjectCard.tsx
    ProjectFilters.tsx
    ProjectHero.tsx
    ProjectGallery.tsx
    ProjectCaseStudy.tsx
  content/
    projects.ts
    profile.ts
  types/
    project.ts
public/
  projects/{slug}/{real-screenshot}.webp
  cv/Sergei_Nikonets_CV.pdf
```

- `projects.ts` — все десять через типизированный `Project` с id, slug, category, short pitch, long intro, features, decisions, tech, media, links, `status`, metadata; не дублировать контент в компонентах.
- Все 10 маршрутов доступны напрямую и статически рендерятся (`generateStaticParams`), `metadata` уникальны для каждого.
- Фильтр категории не должен менять иерархию или скрывать проекты по умолчанию. Поддержать ссылку на выбранную категорию через URL query либо path, и корректное поведение Back.
- Элементы настоящей семантики: `header`, `nav`, `main`, `article`, `section`, `h1`/`h2`; контраст, focus-visible, alt, клавиатурная навигация.
- Настоящие картинки в `next/image`, размеры заданы, WebP/AVIF и lazy loading ниже первого экрана, без сдвигов layout.
- Галерея и видео **не мешают** загрузить страницу; не грузить десять 3D сцен прямо на главной.
- Минимальный клиентский JS, максимум серверных/статических компонентов.
- No fake metrics, fake testimonials, fake badges, broken links, infinite loaders.
- SEO: title/description, OG-изображения, sitemap, structured data Person/CreativeWork при корректности фактов.
- Не публиковать в HTML личный телефон, если не дано прямое отдельное разрешение; Email/GitHub/LinkedIn достаточно.
- Проверить все ссылки, `target=_blank` снабжать `rel=noopener noreferrer`.

## 6. Контент и позиционирование

Предлагаемый hero:

> **Senior Frontend Engineer · Independent Product Builder**  
> **Ideas into working things.**  
> I build thoughtful interfaces and ambitious web products — from complex data tools to interactive games and simulations. Production engineering experience, product curiosity, and AI-assisted development.

Тон: человеческий, уверенный и предметный, без обещаний «revolutionizing the industry» и без пустых «passionate / innovative / cutting-edge». Отдельно дать понять, что коммерческий опыт — это не игры, а крупные реальные продукты.

Принцип для каждого проекта: **замысел → специфический опыт пользователя → 2–4 инженерных решения → что реально доступно**. Писать на языке возможностей и технических решений, а не длинным списком зависимостей. Если нет численных метрик, не придумывать их.

## 7. Что проверить перед публикацией

- Всего **ровно 10** проектов — каждый в All, каждой категории и на уникальной URL-странице.
- Сумма категорий 3+2+5=10, отсутствие раздела featured/secondary.
- Одинаковая визуальная важность всех карточек и одинаково глубокая структура страниц; индивидуальность через контент и медиа.
- Проекты Maeth и Two Towers, Presenter и Lesson Player объясняются раздельно — их отличие очевидно.
- Полные и рабочие демо/репозитории только там, где URL подтверждён; никаких заглушек `#` под видом кнопок.
- Проверены реальные скриншоты, права на изображения, корректные названия брендов и fan-made disclaimer.
- Все десять открываются напрямую, работают браузерные Back/Forward, фильтры работают по клавиатуре.
- Production build, lint, TypeScript check, тесты и Lighthouse на mobile/desktop.
- Проверены 360/390/768/1024/1440 px, отсутствие горизонтального скролла, крупные изображения не распирают верстку.
- `prefers-reduced-motion`, focus-visible, осмысленный alt, хороший контраст, браузер без JS хотя бы показывает контент.
- Страницы не требуют авторизации, если это не особенности самого демо.

## 8. Как работать с Codex: порядок

1. Сначала обследовать текущий репозиторий: посмотреть файлы, существующий стек, скрипты и `AGENTS.md`. Прочитать этот документ, HTML-макет и, если доступен, JSON. Если доступны оригинальные README, сверить каждый проект. Отметить расхождения; приоритет у актуального README и реального поведения приложения, а не у краткого JSON.
2. Если репозиторий пуст, инициализировать Next.js App Router + TypeScript + Tailwind. Если проект уже есть, развивать существующий без ненужной переустановки и переписывания. Реализовать цельный сайт с десятью project routes и типизированным контентом.
3. Использовать визуальные заглушки только до появления настоящих кадров; ни одной выдуманной «фотографии приложения».
4. Сделать мультимедиа-систему, чтобы реальные скриншоты можно было просто положить в `public/projects/<slug>/` и описать в данных.
5. Подключить подтверждённые ссылки, добавить профиль и CV только из предоставленных файлов.
6. Проверить `npm run build`, типы, линтер, 10 маршрутов, фильтры, все размеры. Исправить ошибки до сдачи.
7. В конце вывести: файлы/маршруты, что реализовано, команды запуска, какие ссылки/медиа ещё требуют подтверждения, какие проверки реально выполнены и что осталось. Не утверждать, что сборка/ссылки/изображения проверены, если проверки не запускались.

**Не запрашивать подтверждения по каждому дизайнерскому решению.** Сделать первую цельную реализацию по ТЗ, после чего можно обсуждать только конкретные правки.

## 9. Критерии приёмки для первой версии

**Готово**, когда сайт можно открыть локально, увидеть все десять проектов в сетке, фильтровать по 3 категориям, переходить на отдельную страницу каждого, читать его характерные особенности и технические решения, вернуться к каталогу, открыть подтверждённые внешние ссылки и прочитать краткую профессиональную биографию. Версия адаптивна, без критичных ошибок и без невидимых/ненастоящих медиа.

Это **не готово**, если есть только красивая главная страница с lorem ipsum, пятью случайно выбранными проектами, декоративными картинками вместо реальных работ, недействующими кнопками или большим количеством бессодержательной анимации.
